The 6 schools below are the user's favorites. When a listing's school_elementary matches one of these names, the listing card and its map price-pill should be visually highlighted so the user can scan for "good school" listings instantly. The match reuses the existing DB column populated by the point-in-polygon school-districts lookup — no distance math, no geocoder calls.

Option A — Subtle Accent

Low visual noise

A 4px green left-border on the listing card + a 2.5px green ring around matching price-pills. The schools row gets a small leading ★ glyph as a non-color signal. The original schools text stays unchanged — the row itself tells the user which school matched. Lowest noise of the three; closest to the production look.

Summary & Recommendation

All three options reuse the existing park-green token #16a34a (with darker #15803d when bg-on-white-text AA contrast is needed) and pair color with a non-color signal (★ glyph, badge text, or border thickness) per the Design Bible "never use color alone" rule. The difference is discoverability vs. visual noise:

  • Option A (Subtle Accent) — closest to production, lowest noise, easiest to miss.
  • Option B (Star Badge) — most discoverable, but adds another badge to an already-dense card and the wording "Top school" is editorial.
  • Option C (Themed Green Pill + Chip) — strongest cohesion with the green 🏫 POI pins that just shipped; the green-pill / green-chip / green-pin trio tells one consistent visual story.
Recommendation: Option C. The school POI overlay is the freshly-shipped context this feature builds on — making the highlight green visually closes the loop: green pin on the map → green price-pill → green school chip on the card. The user learns "green means favorite school" once and applies it everywhere. The two cons (green-pill could read as "good price"; requires a Jinja template change) are addressable: the ★ prefix on the pill disambiguates "star = school, not price," and the template change is small (~6 lines in [`listing-card.html`](web/templates/partials/listing-card.html:163)). If the false-signal risk worries the user, a strong fallback is Option A + Option C's schools-row chip (subtle accent on the card, keep the white pill, but chip the matching school in the schools row) — call it Option C-lite.

Open Questions for the User

  1. Full-name vs. abbreviated-name matching. The DB stores "Cherry Chase Elementary"; the [`abbreviate_school`](web/dependencies.py) filter shortens it to "Cherry Chase Elem" for display. The match logic must compare against the full DB name, not the display string. Three implementation options for the favorites source-of-truth:
    • (a) Python constant in [`web/dependencies.py`](web/dependencies.py) — FAVORITE_SCHOOLS = {"Cherry Chase Elementary", …}. Simplest, server-rendered, zero JS. UX Designer's pick for this iteration.
    • (b) Jinja context passed from the route — flexible if favorites become per-user later.
    • (c) API endpoint + client-side compare in map.js — needed only if favorites can be edited live without reload.
    The 6 favorites are currently hardcoded in the POI layer too — recommend matching that pattern (a) until per-user favorites become a real feature.
  2. Middle / High school favorites. Should the highlight escalate (stronger color, second chip) when middle or high school is also a favorite? Or treat elementary as the only signal (current task scope)? Recommend: elementary only for v1; revisit if/when middle/high favorites are introduced.
  3. Badge wording (Option B only). "★ Top school" is editorial — implies a ranking we don't have. Alternatives: "★ Favorite school", "★ Saved school", or just "★ School". Skip if you go with A or C.
  4. Hover / selected-state interaction. The price-pill already has .highlighted (card↔map sync) and .selected (click) states. Should .is-fav-school + .highlighted intensify (e.g., bigger ring, deeper green) or just additively apply both? Recommend additive — Code mode can implement and the UX Designer will spot-check.
