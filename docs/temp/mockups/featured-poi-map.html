Featured POI Treatment — 3 Design Options

User wants to add Ortega Park (a Sunnyvale city park) to the map as a "featured" point of interest — visually distinct from the regular green 🌳 park POIs already in the system. Pattern must be extensible to future featured POIs (a featured workplace, featured school, etc.) and coexist with the price-pill markers (price = primary signal per Design Bible) and the favorite-school 🏫 green pins shipped 2026-06-03.

Option A — Larger ringed pin + always-shown label

★ Recommended Highest scannability

36×36px pin (1.5× the regular 24×24 POI) using the same category color & emoji (green 🌳 for a featured park, indigo 🏢 for a featured workplace, etc.), wrapped in a dark 3px ring with a white separator and a deeper drop shadow. A small pill-shaped "Ortega Park" label is anchored below the pin at all times. Three non-color signals: size, ring, and persistent text — works for users who can't see the ring color at all. Hover/focus promotes the label to accent-blue and reveals a richer popup ("Park · 12 acres · 0.4 mi from listings").

Pros

  • First thing the eye finds — biggest, darkest outline on the map.
  • 3 non-color signals (size + ring + text) — strongest accessibility story.
  • Name visible without interaction — no hover required to identify.
  • Pattern scales cleanly to any category (just swap the emoji + bg color).

Cons

  • Largest footprint — at zoom <12 it can overlap nearby price pills (mitigated by z-index + few featured POIs).
  • Always-on label feels heavy if user later promotes 4+ POIs to featured.

Accessibility

  • Ring contrast: 14.7:1 against any category color (WCAG AAA).
  • Label text on white: 16.1:1 (AAA).
  • Focus ring: 2px accent blue, 3px offset.
  • Color-independent — usable in grayscale.

Tradeoffs

  • Maximum prominence ↔ maximum footprint. Best if featured POIs stay rare (1–3 ever).

Option B — Star badge + always-shown label chip

Consistent with shipped ★-favorite pattern

Standard 24×24 POI dot (same as any regular park) with a small ★ badge overlaid in the top-right corner in accent blue (#2563eb), plus an always-visible "★ Ortega Park" chip anchored below. Re-uses the exact "add a ★ to mean favorite" mental model that shipped yesterday for favorite schools — same glyph, same semantic. The chip is the only thing that grows beyond the regular POI footprint, so the map stays compact.

Pros

  • Reuses the ★ glyph already in production for favorite schools → consistent vocabulary.
  • Same footprint as a regular POI (only the chip adds height).
  • Two non-color signals (★ glyph + chip text) without changing pin size.
  • If the system later supports user-toggleable "featured" toggling, ★ is the natural affordance.

Cons

  • The 14px star badge is small — at default desktop zoom it competes with the emoji for visual space inside 24px.
  • "Featured" and "favorite" become the same glyph — could blur the distinction (workplace can't be "favorited", but it CAN be "featured").
  • Less prominent than Option A; eye may skip over it when scanning a busy map.

Accessibility

  • ★ badge contrast: 5.1:1 (white on accent blue) — AA.
  • Chip text on white: 16.1:1 (AAA).
  • Color-independent — works in grayscale via ★ glyph.
  • Caveat: ★ at 9px font size approaches the lower bound for users with low vision.

Tradeoffs

  • Vocabulary consistency ↔ semantic ambiguity. Best if the team is comfortable conflating "featured" and "favorite".

Option C — Teardrop pin marker

Strongest shape contrast New shape vocabulary

Drops the divIcon circle entirely and uses a classic teardrop "map pin" shape (32×42 bounding box) that points down at its target. Sits visually "on top of" the map rather than embedded in it. Always-shown dark label sits beneath the pin tip. The shape itself is the differentiator — even at a glance with no color, it reads as different category of marker from the circular POIs and the rectangular price pills.

Pros

  • Shape alone distinguishes it from circle POIs and rectangular price pills — color-independent.
  • Tip points to the exact coordinate (a precision wins over the centered-circle POIs).
  • Universally recognized as "this is a place marker" (Google Maps, Mapbox use this shape).
  • Tallest of the three — strong vertical presence.

Cons

  • Introduces a new shape vocabulary — every other POI on the map is a circle.
  • The dropped-pin shape feels heavier and more "marker on top of map" than the embedded-circle pattern; it can feel out of place against the flat-circle POI style.
  • CSS-rotated border-radius trick needs counter-rotation for the glyph — slightly more brittle than the circle implementation.
  • Risk: looks similar to Leaflet's default L.marker teardrop icon, which may confuse users into expecting default popup behavior.

Accessibility

  • White 2.5px border ensures separation from any tile color.
  • Label (dark bg, white text): 16.1:1 (AAA).
  • Shape independence: passes a color-blind / grayscale test cleanly.

Tradeoffs

  • Strongest visual differentiation ↔ inconsistent with existing POI shape language.

Recommendation: Option A (Larger ringed pin + always-shown label)

Option A wins on the three criteria that matter most for this feature: (1) at-a-glance scannability — the dark ring + size combo reads as "primary place" before the eye registers the green color; (2) accessibility — three independent signals (size, ring, label) means it works even in grayscale, even at low vision; and (3) extensibility — the pattern is "category color/emoji + featured wrapper", which means a featured workplace, featured school, etc. only requires swapping the inner color & glyph, never touching the wrapper.

Option B is a strong second if vocabulary consistency with the favorite-school ★ pattern is more important than maximum prominence. It's also the right choice if the team expects featured POIs to grow to 4+ entries (its 24×24 footprint scales better than A's 36×36).

Option C is the most visually distinctive but introduces a new shape vocabulary that competes with — rather than complements — the existing circular POI system. Not recommended unless the team wants to lean fully into "Google Maps starred-place" semantics.

Discarded direction — pulse/breathing animation. Considered (would have been Option D). Rejected because: (1) violates user attention budget against the more important price pills, (2) requires prefers-reduced-motion fallback that effectively reduces to Option A or B anyway, (3) animated halos compete with marker-cluster expansion animation already in production.

Recommended hover/click behavior

All three variants should use the same hover-popup pattern for behavioral consistency:

  1. Always-shown label (name only) — eliminates the "what is this?" question.
  2. Hover reveals a richer popup: Park · 12 acres · 0.4 mi from 3 listings (acreage + distance to nearest listings; computed by Code mode).
  3. Click behavior — same as regular POIs today (no special handler); the popup-on-hover is enough. Leaves room for a future "filter to listings near this POI" affordance.

Data-model recommendation (UX call — Code mode to confirm)

Per-entry boolean

{
  "id": "poi_ortega_park",
  "category": "park",
  "featured": true,
  "name": "Ortega Park",
  ...
}

Add a featured: boolean field on each POI entry in interest-points.json. Default false. UI checks the flag in createPOIMarker() and swaps the icon HTML.

Why: minimum schema change, mirrors the SCHOOLS isFavorite pattern, no separate list to keep in sync, user-managable from the POI panel later (a "★ Feature" toggle).

Separate featured array

{
  "featured_pois": [
    "poi_ortega_park"
  ],
  "points": [ ... ]
}

Top-level array of POI IDs that are "featured". loadPOIs() cross-references on render.

Why not: introduces a second source of truth that has to stay in sync with points; orphan IDs become a silent bug class.

Hardcoded constant

// map.js
var FEATURED_POIS = [
  'poi_ortega_park'
];

Like the existing SCHOOLS + FAVORITE_SCHOOLS hardcoded list.

Why not: user-added POIs live in JSON, so the "featured" flag should also live there. Hardcoded list means a code deploy is needed to feature a new POI.

Open questions for the user

  1. Featured POI count. Realistically how many featured POIs do you expect — ever 1–3, or could it grow to 5–10? (A's 36×36 footprint starts to feel heavy past 3; if you want 5+, switch the rec to B.)
  2. Featured = user-togglable, or admin-only? If user-togglable from the POI panel, Option B's ★ glyph maps naturally to a "star this POI" button (matches favorite-school semantics). If admin-only (you edit the JSON directly), Option A's "this is a curated landmark" framing fits better.
  3. Should the featured pin show on top of price pills if they overlap? Current POIs render below price pills (zIndexOffset: -100). A featured pin "competing" for the same pixel as a price pill — which wins? Recommendation: featured pin wins (it's rare and the user explicitly cares about it), but confirm.
  4. Hover popup content. Is "Park · 12 acres · 0.4 mi from 3 nearby listings" the right hover content, or just name+category? (Code mode needs the distance-to-listings calc spec.)
  5. Featured POI panel treatment. Should featured POIs be visually distinguished in the left-side POI panel too (e.g., pinned to the top of the list with a ★)? Out of scope for this mockup but worth a follow-up.
